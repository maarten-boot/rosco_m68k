# libs sst_flash: no timeout, no interrupt masking and no verify (updateflash can hang or write a bad ROM)

**Affects:** release v2.42 and `develop` @ ec229f9 (r2.x, default build)
**Found by:** code review of v2.42 plus runtime tests in MAME (`rosco_m68k_010`); details in docs/planning/tests/ (branch `planning/session-docs` on maarten-boot/rosco_m68k)
**Status:** Confirmed in MAME with the flash-ROM model (rosco-emulator branch feature/sst-flash): programming 0xFF over 0x00 reported success; erase/program with interrupts enabled crashed ("Illegal instruction" from the tick handler). Fixed versions pass, incl. a full updateflash 2.42 -> 2.42.1.
**Review IDs:** D-17

## Description
- `wait()` polls DQ6 with no limit, so a missing/protected/failing chip hangs the caller forever (with interrupts masked, in updateflash).
- Nothing masks interrupts inside the library, although the vectors and handlers live in the ROM being programmed: while the chip is busy it returns status bits, so an interrupt executes garbage. updateflash masks itself, other callers may not.
- No verification: a byte that does not program (e.g. its sector was not erased – flash can only clear bits) or a sector that does not erase is reported as success, so a bad ROM image can be written without any error.

## Where (develop @ ec229f9)
- `code/software/libs/src/sst_flash/sst.c:31 (wait)`
- `code/software/libs/src/sst_flash/sst.c (sst_sector_erase, sst_write_byte, sst_get_device_info)`

## How to reproduce
`tests/flash/sst_verify_irq_test.c` and `tests/flash/updateflash_harness.py` on the flash-ROM emulator; `tests/sst_timeout_test.c` + `mame/sst_stuck.dbg` for the timeout.

## Proposed fix
Bound the wait (1,000,000 polls ≈ 5 s at 10 MHz); run each command sequence at IPL 7 and restore the caller's mask; read back each programmed byte and check erased sectors are all 0xFF. sst_chip_erase is masked but not verified (device-size dependent).
